# Gate D.3 — fenced execution, resourceVersion CAS, terminalization

**Status: PASSED**

Sanitized. No credentials, no bearer tokens, no model reasoning. Every result
below is a real response from Google infrastructure or from real Firestore
transactions. Synthetic data only.

Builds directly on [`gate-d3a-cloud-run-resourceversion-cas.md`](gate-d3a-cloud-run-resourceversion-cas.md),
which established that Cloud Run v1 `replaceService` enforces
`metadata.resourceVersion` while v2 `services.patch` ignores `etag` entirely.

## The property being defended

Distributed exactly-once execution across Firestore and the Cloud Run Admin API
is not achievable and is not claimed. What is defended is five layers:

| # | Layer | Enforced by |
|---|---|---|
| 1 | Only the current owner may advance execution state | Firestore transaction on owner + `lease_epoch` |
| 2 | An obsolete Service snapshot cannot overwrite a newer one | Google, HTTP 409 ABORTED |
| 3 | Every duplicate request can only request the SAME authorized effect | decision-bound target pinning |
| 4 | Crash boundaries are resolved by reading reality | reconciliation |
| 5 | A verified execution can never be re-run | terminal state |

**The honest residual is stated in full at the bottom of this file.**

## D3.1 / D3.2 — lease epochs and ownership-bound transitions

`lease_epoch` is generated by the execution plane, never supplied by a caller,
immutable for one ownership period, and incremented on every expired-lease
takeover. Acquisition returns `execution_id`, `lease_owner`, `lease_epoch`,
`lease_expires_at` and `state`.

Every worker transition is one Firestore transaction asserting **all five** of:
not terminal, owner matches, epoch matches, lease unexpired, current state in
the expected set.

### Live proof — worker A stalls, worker B takes over, A wakes up

Real `execution-state` database, real transactions.

```
A acquires                              ACQUIRED, epoch 1
B attempts while A's lease is live      HELD_BY_OTHER
   ... A's lease expires ...
B takes over                            RECOVERED, epoch 2      (epoch incremented)

worker A wakes up holding epoch 1:
  renew lease                           FENCED_OUT
  advance -> PRECONDITION_CHECKED       FENCED_OUT
  advance -> MUTATED                    FENCED_OUT
  advance -> VERIFIED (terminal)        FENCED_OUT
  advance presenting B's epoch          FENCED_OUT
  advance impersonating B's owner id    FENCED_OUT

state after every stale attempt         CLAIMED        (unchanged)
owner after every stale attempt         worker-B       (unchanged)

worker B proceeds:
  -> PRECONDITION_CHECKED               ADVANCED
  -> MUTATION_REQUESTED                 ADVANCED
  -> MUTATED                            ADVANCED
```

**Test A and Test B pass:** a stale owner can neither advance state nor renew
its way back into ownership. Forging the epoch does not help, because the owner
must match too; forging the owner does not help, because the epoch must match
too.

## D3.3 — final ownership check before the mutation snapshot

`PRECONDITION_CHECKED` is written immediately before the Cloud Run read.
Because that write is ownership-bound, reaching it proves the lease was ours at
that instant, and a fenced worker therefore never fetches a `resourceVersion`
at all. A second ownership-bound write to `MUTATION_REQUESTED` gates the
mutation itself. The snapshot is read exactly once and passed into the
mutation, so a lost lease can never be papered over by re-reading a fresher
precondition.

## D3.5 — the stale-owner race, stated honestly

Firestore fencing is proven above: a stale worker cannot advance state, cannot
renew, cannot terminalize. Cloud Run OCC is proven above: a stale snapshot is
rejected by Google.

**What is NOT claimed:** that a fenced worker is physically incapable of
reaching the Cloud Run API. If worker A loses its lease *after* its final
ownership check, and nothing else has changed the Service in the interim, A's
`resourceVersion` is still current and Google will accept its request.

Why that is safe rather than merely unlikely:

- A can only ever request the **exact** `authorized_target_revision` from the
  persisted decision. It cannot choose a different revision, service, or
  percentage. The effect is therefore identical to the one already authorized —
  effect-idempotent.
- A cannot record that it acted. The state write is fenced (`FENCED_OUT`,
  logged at ERROR as `execution_state_write_fenced`).
- The next owner does not trust any of that. It re-reads real infrastructure
  and reconciles, so a duplicated identical effect converges rather than
  compounding.

This window is a property of two systems that cannot be committed together. It
is narrowed by both layers and closed by neither alone.

## D3.6 — the authorized target is immutable

`ExecuteRequest` and `TerminalizeRequest` accept exactly `incident_id` and
`decision_id`, with `extra="forbid"`. Attempts to supply `target_revision`,
`authorized_target_revision`, `resource_version`, `percent`, `target_ref`,
`action_type`, `verdict` or `force` are rejected with `422`. The target comes
from the authoritative decision; the `resourceVersion` comes from the
executor's own authorized read. Neither can come from request JSON.

## D3.8 / D3.9 — terminalization

After mutation the execution is `MUTATED`. The independent verifier — a
different service under a different read-only identity — must then observe the
exact authorized revision at exactly 100% of traffic with nothing else serving,
plus a healthy response. Only then is the execution terminalized to `VERIFIED`,
and only then may the incident become `RESOLVED`.

Terminalization is gated on state (`MUTATED`, compare-and-set) plus the
executor's own re-observation of the live service, rather than on a lease: it
performs no mutation, and the mutating worker's lease may legitimately be long
gone. Two separate identities must therefore agree before an incident closes.

**An incident is never resolved while its execution is still recoverable as
`MUTATED`.**

### Test E / Test F — terminal means terminal

```
terminalize                    ADVANCED
terminalize again              ALREADY_TERMINAL
advance after terminal         ALREADY_TERMINAL
10 acquisitions after lease expiry   all ALREADY_FINISHED
lease_expires_at               null       (cleared)
state                          VERIFIED
```

Terminality is checked **before** lease expiry in `acquire`, so a lapsed lease
can never reopen a finished execution.

## D3.14 — a compromised control-plane writer

Gate D.1 prevents the **executor** from forging authorization: it is read-only
on `(default)`. It does **not** protect against full compromise of the
authoritative policy/control-plane writer.

A cheap uniqueness invariant fitted without schema upheaval and was
implemented. An *authorization fingerprint* is derived from
`incident_id | action_type | target_ref | authorized_target_revision |
policy_version | evidence_snapshot_hash`, and the execution plane binds one
fingerprint to exactly one execution identity, transactionally, first-writer-
wins. The executor holds no delete right on that database, so a binding cannot
be retracted.

Live:

```
bind first                              BOUND
bind again, same execution identity     SAME
bind an equivalent second decision      CONFLICT   -> DUPLICATE_AUTHORIZATION, no mutation
```

**Scope of the guard, stated plainly:** it stops an *equivalent* re-issued
decision from becoming a second infrastructure effect. A fully compromised
authoritative writer can still author a *materially different* authorization,
which by definition has a different fingerprint. That remains an open
limitation.

## Honest limitations after Gate D.3

1. **Not globally exactly-once.** Firestore and the Cloud Run Admin API cannot
   be committed together. The claim is fenced, duplicate-safe, recoverable,
   effect-idempotent execution with reconciliation.
2. **The stale-worker window is narrowed, not eliminated.** A fenced worker
   that already passed its final ownership check can still reach Cloud Run if
   the Service has not changed. It can only apply the same authorized effect,
   and it cannot record having done so.
3. **Audit is tamper-evident, not immutable.** A compromised authoritative
   writer could rewrite the chain and the tail metadata together.
4. **Control-plane compromise is only partly addressed.** The fingerprint
   invariant stops an equivalent re-issue, not a materially different forged
   authorization.
5. **Candidate freshness is point-in-time.** The target was healthy immediately
   before the mutation; nothing guarantees it stays healthy.
6. **Firestore isolation is database-level**, not collection-level.
7. **Cloud Run v2 `etag` is not a concurrency control** for this call, and is
   never claimed as one.
8. **Model Armor is not integrated**; no prompt-injection resistance is claimed.
   **No Cloud Trace span exists.** Complete Australian data residency is
   **not claimed**. Only the Systems Investigator is deployed; the Network,
   Security and Continuity investigators are contracts, not runtimes.
